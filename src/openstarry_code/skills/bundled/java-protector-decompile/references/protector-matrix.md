# Protector Matrix

Use this matrix to classify a protected Java artifact before attempting recovery.

## ZKM / Zelix KlassMaster

Official positioning includes Java decompilation resistance through flow obfuscation, string encryption, integer constant encryption, reference obfuscation, method parameter obfuscation, and related transformations.

Indicators:

- References to `Zelix`, `KlassMaster`, or `ZKM` in metadata, scripts, logs, or weakly cleaned artifacts.
- Many small renamed classes, fields, and methods with preserved package/resource entrypoints.
- Decompiler output with invalid control flow, aggressive exception paths, bogus branches, or code that compiles poorly.
- String literals absent or replaced by short encrypted blobs and runtime decryptor calls.
- Reflection-heavy access to renamed classes or methods.

Start:

1. Use multiple decompilers, but treat mismatches as signals of flow obfuscation.
2. Inspect bytecode with `javap -v` or Recaf when Java source is nonsense.
3. Find string decryptor methods by locating loops over `char[]`, `byte[]`, XOR/add/sub, `StringBuilder`, `new String`, or `intern`.
4. Run a minimal harness or Java agent to call decryptors under the real classpath.
5. Rename entrypoint-adjacent classes first; do not attempt full project-wide deobfuscation up front.

## JNIC / Java Native Obfuscator / Native-Obfuscator

JNIC-style protection moves selected Java method bodies into native libraries and leaves Java stubs, native methods, or loader glue. JNIC documentation says it can process output from Java obfuscators such as Zelix KlassMaster or Stringer, so expect stacked protection.

Indicators:

- JAR contains `lib/*.so`, `*.dll`, `*.dylib`, `*.jnilib`, or OS/architecture-specific native resources.
- Many Java methods are marked `native` or call a small loader before meaningful logic.
- Native library contains `JNI_OnLoad`, `RegisterNatives`, `Java_...` exports, or strings resembling Java class descriptors.
- Java side extracts a native library to temp paths and calls `System.load` or `System.loadLibrary`.
- Meaningful Java bytecode is missing from methods that should contain business logic.

Start:

1. Map Java native methods and class descriptors.
2. Locate library extraction and load order.
3. In native code, find `JNI_OnLoad`; trace calls to `RegisterNatives`.
4. Build a table: Java class, Java method, descriptor, native function pointer, native address.
5. Hook JNI helper calls to recover strings, arrays, byte buffers, and object fields crossing the boundary.
6. If the native library is VMP/Themida-protected, switch to native protector workflow and focus on boundary traces.

## Stringer, Allatori, DashO, ProGuard, R8

Indicators:

- `ProGuard` or `R8` often means minification/shrinking, not necessarily heavy protection.
- Allatori/DashO/Stringer-style artifacts often show string decryptors, reflection indirection, class loader tricks, or invokedynamic bootstraps.
- `META-INF` files, Maven metadata, stack traces, service providers, and resource names may preserve useful names.

Start:

1. Separate minification from protection. If control flow is intact, prioritize renaming and entrypoint reconstruction.
2. Search for decryptor calls and bootstrap methods before browsing thousands of renamed classes.
3. Inspect `BootstrapMethods` for invokedynamic-based dispatch or string recovery.
4. Use runtime instrumentation when decryptors depend on class identity, stack traces, or call site constants.

## VMProtect / VMP / Themida / Code Virtualizer

These protect native code, not Java bytecode directly. In Java targets they usually appear on JNI libraries generated by JNIC/native-obfuscator or manually written native components.

Indicators:

- Native library contains `.vmp0`, `.vmp1`, `.vmp`, `.themida`, `.winlice`, or strings referencing VMProtect/Themida.
- Imports are sparse or resolved dynamically.
- Function bodies show dispatcher loops, indirect jumps, handler tables, opaque predicates, or anti-debug checks.
- Java side has a small JNI bridge and the decisive logic is in native code.

Start:

1. Identify JNI boundary first. It is often cheaper than full devirtualization.
2. Trace input/output at the native method boundary.
3. Break after unpacking or after library initialization if a packer is present.
4. Use Ghidra/IDA for structure, Frida/x64dbg/lldb/gdb for runtime, and native reverse skills for VM handler mapping.
5. Only attempt full VM devirtualization when boundary tracing cannot answer the task.

## Confidence Labels

- Strong: explicit protector strings, sections, class names, native exports, or documentation artifacts.
- Medium: multiple structural indicators match and runtime behavior supports the hypothesis.
- Weak: only naming shape or decompiler failure; confirm before committing to a route.

## Source Notes

- Zelix KlassMaster feature pages describe flow obfuscation, string encryption, integer/long constant encryption, reference obfuscation, and method parameter transformations: `https://www.zelix.com/klassmaster/features.html`
- Zelix string encryption documentation describes encrypted string literals in class-file constant pools plus runtime decryptor fragments: `https://www.zelix.com/klassmaster/featuresStringEncryption.html`
- JNIC describes itself as a Java native obfuscator and documents compatibility with existing obfuscators such as Zelix KlassMaster and Stringer: `https://jnic.dev/` and `https://jnic.dev/documentation/`
- VMProtect documentation describes virtualization, mutation, and combined mutation plus virtualization: `https://vmpsoft.com/vmprotect/user-manual/`
- Recaf describes itself as a Java bytecode editor for high- and low-level bytecode editing: `https://github.com/Col-E/Recaf`
